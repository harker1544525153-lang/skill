# 前端系统 PRD 文档与功能列表生成技能（通用版）

## 一、适用场景

将**任意指定前端源码目录**下的页面功能，整理为专业 PRD 文档与功能列表 Excel。
本技能**不绑定任何具体项目结构**：

- **输入目录**：任意前端项目根目录（Vue / React / 配置式路由 / 目录约定式路由均可）
- **输出目录**：任意指定位置
- **产品名 / 文档名**：任意定义（如"某某管理系统""数据中台"）
- **版本号**：任意定义（如 V1.0、V2.3、2026.09），贯穿文档标题、文档信息表、修订记录与 Excel 表名
- **模块层级**：不预设固定级数，**根据实际代码结构（路由/菜单/页面嵌套）动态推导**，层级深度、编号规则均自动适配

## 二、工作流程

### 阶段1：分析实际代码结构（结构转化）

**目标**：把前端代码组织方式转化为「模块树」。不同项目代码结构不同，先识别再转化：

| 代码特征 | 识别方式 | 转化为模块树的规则 |
|----------|----------|--------------------|
| 菜单/导航 | `layout/*`、`config/menu*`、`router` 中 `meta.title` | 菜单一级 → 模块 1 级；菜单二级 → 页面 2 级 |
| 路由层级 | `router/index.*` 的嵌套 `children` | 嵌套深度与菜单一一对应；无菜单的动态路由（如 `/xxx/:id`）按面包屑落位到父级下作为子项 |
| 页面内 Tab/抽屉/向导 | 页面组件内的 `el-tabs`、`tabs`、`步骤条` | Tab 页 → 下一级子项；**父页面只显示标题，内容下放到子 Tab** |
| 页面文件组织 | `pages/**`、`views/**`、`components/页面相关` | 目录/文件与页面归属对应，作为兜底校验 |
| 数据与业务逻辑 | `composables/**`、`hooks/**`、`stores/**`、`api/**` | 提取"数据来源/聚合逻辑"，写入业务逻辑与字段数据来源 |

**通用转化步骤**：
1. 读取路由配置与菜单布局 → 构建模块树骨架（编号 + 名称）。
2. 逐页面读取组件源码 → 提取功能说明、输入/输出字段、交互操作、业务逻辑。
3. 读取数据层源码 → 补充字段的 `数据来源` 与页面的 `业务逻辑`。
4. 校验：菜单 → 路由 → 页面文件三者的名称/层级一致性，不一致时以「菜单显示」为准。

### 阶段2：构建通用模块数据模型

**不预设层级深度**，使用通用的递归节点结构（深度任意，按实际代码推导）：

```python
{
    "code": "4.1.1",        # 编号（自动生成或用户指定，可任意深度，如 "1"、"1.2"、"1.2.3"）
    "name": "页面名称",       # 纯名称（渲染标题、Excel 使用，不带编号）
    "route": "一级菜单 / 二级菜单 / 页面名称",   # 面包屑路径（可选）
    "children": [ ... ],    # 子项列表（深度不限；无子项时省略或空）
    "funcs": [              # 功能说明：第1条为概述（核心定位+整体作用+所有能力），其余为补充
        "1. 概述：……（一句话概括核心定位、整体作用与全部能力）",
        "2. 能力一：……",
        "3. 能力二：……",
    ],
    "io": {
        "input": [          # 输入字段表（列：区域/字段/字段类型/是否必填/默认值/数据来源/说明）
            {"area": "表单区", "field": "字段名(业务名)", "type": "string",
             "required": "是", "default": "空",
             "source": "所属系统页面字段（业务口径）", "remark": "约束/联动说明"},
        ],
        "output": [         # 输出字段表（列：区域/字段/数据来源/说明）
            {"area": "导出", "field": "导出文件名模板",
             "source": "本地生成/业务口径", "remark": "去向与副作用"},
        ],
    },
    "logic": "业务逻辑：按场景说明数据来源与不同场景下的处理/展示状态（业务口径）。",  # 业务逻辑：数据来源 + 不同场景展示状态
    "ops": [                # 交互操作：默认仅入 Excel
        "操作名称：操作位置（…），操作方式（…），展示内容（…）",
    ],
}
```

**字段类型（type）用英文枚举**，渲染时翻译为中文：`number / string / boolean / array / object / date / datetime / file / image / text / select / json / enum / tree / route / param / query` 等。

**编号生成规则**（可配置）：
- 默认自动：按模块顺序递增，如 1、2、3…；子级 1.1、1.2…；孙级 1.1.1…；以此类推，深度不限。
- 可自定义起始编号（如从 4 开始 → 4、4.1、4.2、4.1.1…）或完全人工指定。
- 编号仅存在于数据模型的 `code` 中；**所有渲染产物（标题、Excel 菜单列）只显示纯名称，不带编号**。

### 阶段3：生成 PRD Markdown（渲染规则）

输出文件：`<输出目录>/<产品名>产品需求文档<版本号>.md`

1. **文档头**：`# <产品名>产品需求文档<版本号>`
   - `## 1 文档信息`：文档信息表（文档名称 / 版本 / 编写日期 / 作者 / 密级 等，可配置列）
   - `### 1.1 修订记录`：版本 / 日期 / 修订内容 表（用户提供 `(版本, 日期, 修订内容)` 列表；日期默认当天）
     - **修订内容规则**：每条**尽量一句话简要描述**本次修订的核心要点，不展开罗列细节；按「要点：概括」句式组织（如「某模块补全：正式挂载『某页签』并补齐权限」「文档质量修正：完善翻译层以消除正文非业务英文残留」），突出重点即可；V1.0 初版写「初版：依据前端源码产出功能模块、字段、逻辑与操作说明」。
   - `### 1.2 编写说明`：层级规则、每个模块包含内容说明（随 include_ops 自动增减"交互操作"条目）
2. **产品概述**：`## 2 产品概述` → 产品背景 + 产品目标（目标表）。内容由用户提供或从项目 README / 需求文档提取。
3. **功能模块详细需求**：`## 3 功能模块详细需求`，按模块树**递归**输出：
   - 标题级别按节点深度映射：1级 `###`、2级 `####`、3级 `#####`、4级及以上 `######`（超过 6 级统一用 `######`）
   - **父节点含 children 时，父级仅输出标题行，内容下放到子节点**；各标题后接 `---` 分隔。
4. **每节点正文内容**：叶子节点在标题行（含编号+纯名称）下方按固定顺序输出 5 个章节；含 children 的父节点不输出正文。缺失的章节自动忽略，生成的格式以渲染结果（MD/Word/Excel）为最终口径：

   **① 功能说明（`**功能说明：**`）** —— 定性描述该节点做什么，首条必须是**概述**，后续条目为能力/场景补充。
   - 第 1 条（概述）：以「概述：」开头的一段话，用一句话概括**核心定位 + 整体作用 + 现有全部能力清单**。定位指本节点在系统中的作用与归属；能力清单按业务维度罗列（认证/守卫、配置、下发、监控等），用「、」或「，」串联。
   - 其余各条：从 `- ` 无序列表，每条约一句，描述一个**具体能力点 / 场景规则 / 展示形态**，如「认证方式：…」「表单校验：…」「状态规则：…」。条目语义要完整可读，不省略主谓语。
   - 每条前的序号编号（`1. `、`2. `）由渲染层剥离，仅保留文本。

   **② 业务逻辑（`**业务逻辑：**`）** —— 说明本节点的数据来源与不同场景下的处理/展示状态，逐条 `- ` 无序列表。
   - 每条以「场景前置：结果」的句式组织，覆盖：表单校验规则、数据生成/刷新时机、失败计数与锁定、守卫/拦截分支、提交成功/失败的不同提示与跳转、对账/合并规则等。
   - 一律**用业务口径**描述数据来源（设备端动态数据 / 所属系统页面字段 / 系统协议报文），不使用「前端 Mock / store / 接口」等技术术语标注。
   - 提示文案用『』包裹；标识符号、函数名等经翻译层中文化后保留可读语义。

   **③ 输入字段（`**输入字段：**`）** —— 表格，表头 `| 区域 | 字段 | 字段类型 | 是否必填 | 默认值 | 数据来源 | 说明 |`。
   - **区域**：字段所在 UI 区域或数据片段，如「XX页」「表单区」「XX配置·XX设置」。
   - **字段**：含义清晰的业务字段名；渲染前剥离「中文名 英文标识」中的英文部分，保留纯中文（如 `名称 name → 名称`）。
   - **字段类型**：用英文枚举（`number/string/boolean/select/date/datetime/array/json/enum/tree/file/image/text…`），渲染时统一翻译为中文（数值/文本/布尔/枚举/…）。
   - **是否必填**：是 / 否；**默认值**：随源数据更新、空或具体取值；**数据来源**：业务来源描述；**说明**：补充约束（长度、格式、枚举集、触发动作、联动提示）。
   - **数据来源具体化**：尽量避免仅写「页面表单输入」，应落到系统页面/协议/设备等实际业务出处（如「XX列表页/已登记业务信息，定时返回业务状态、业务信息」「设备端下发报文」，按项目实际填写）。

   **④ 输出字段（`**输出字段：**`）** —— 表格，表头 `| 区域 | 字段 | 数据来源 | 说明 |`。
   - **区域**：输出归属（认证、导出、下发、登录前守卫等）；**字段**：输出项名称；**数据来源**：业务来源（接口返回 / 本地持久化数据 / 设备下发报文）；**说明**：触发的去向与副作用（跳转、下载、写库、提示）。

   **⑤ 交互操作（`**交互操作：**`）** —— 默认仅输出到 Excel「操作项」列，MD/Word 需 `include_ops=True` 才输出。
   - 固定句式：`操作名称：操作位置（…），操作方式（…），展示内容（…）`；必要时追加操作前置条件/触发弹窗提示。
   - 每条覆盖「在哪里」（操作位置）→「怎么操作」（操作方式，含按钮/快捷键/二次确认）→「看到什么」（展示内容，含成功/失败/禁用态提示）。
5. **中文翻译层**：渲染前对文本做 `cn_translate()`——路由 path → 中文菜单名、英文页面/组件/composable 标识符 → 中文。维护 `ROUTE_CN`（路由→中文）与 `FIELD_CN/TOKEN_CN`（英文术语→中文）词典，**按长度倒序匹配避免子串冲突**；词典可按项目追加。

### 阶段4：生成功能列表 Excel

输出文件：`<输出目录>/<产品名>功能列表说明书<版本号>.xlsx`

- **工作表名**：`功能列表说明书<版本号>`
- **表头列数自适应**：`N 列菜单 + 描述 + 操作项`，其中 N = 模块树实际最大深度（如项目最深 5 级 → 7 列：一级~五级菜单/描述/操作项；仅 3 级 → 5 列）
- **列宽**：各菜单列 `12/16/16/…`（首列 12，其余菜单列 16），**描述列最宽（65）**，操作项列 40
- **行高**：表头 24pt，数据行 22pt（紧凑合理留白）
- **样式**：表头深蓝 `1F497D` 底 + 白字加粗微软雅黑 10pt；数据微软雅黑 9pt；全表 `CCCCCC` 细边框；`wrap_text` 垂直居中左对齐
- **内容规则**：
  - 各级菜单列**纯名称、无序号**（渲染前用正则 `^\s*\d+(?:\.\d+)*\s+` 去除编号）
  - **合并单元格**：从 1 级起逐列纵向合并（记录各层级起止行，`merge_cells` 应用）；父节点含子项时父级行只填到该级菜单列，子级内容在后续行展开
  - **描述列**：仅输出功能说明第 1 条概述（一句话概括），其余各条与业务逻辑不展示（`\n` 换行）
  - **操作项列**：仅展示操作名称（冒号前的名称），去掉"操作位置/方式/内容"部分，多个用 `、` 分隔

### 阶段5：MD 转 Word（可选）

输出文件：`<输出目录>/<产品名>产品需求文档<版本号>.docx`

- 字体：微软雅黑（eastAsia 同设），正文 10pt
- 标题样式：H1 18pt / H2 16pt 深蓝 `1F497D`；H3 14pt / H4 12pt 蓝 `2E74B5`；H5 11pt / H6 10.5pt 灰阶
- 表格：`Table Grid` 居中，表头 `D9E2F3` 底色加粗 9pt，**紧凑行高（表头 18pt / 数据 16pt，AT_LEAST），行距 1.0、段前段后 0pt**
- 列表：`List Bullet`；引用块：斜体灰字缩进；代码块：Consolas 9pt 缩进

```bash
# 依赖
```

## 六、注意事项

1. **结构转化准确性**：模块层级以「实际代码结构」为准——先识别框架与代码组织方式，再推导模块树；菜单、路由、页面文件三者不一致时以菜单显示为准。
2. **父级只显标题**：父节点含子项时，父级仅输出标题，具体内容放在子项中展示（避免重复）。
3. **纯名称无序号**：所有渲染产物只显示纯名称；编号仅存在于数据模型 `code`，按需自动生成。
4. **深度自适应**：Markdown 标题级别、Excel 菜单列数均随模块树实际最大深度动态调整，无需预设级数。
5. **中文翻译**：所有渲染文本必须过翻译层，保证字段/路由/术语全中文；词典按长度倒序匹配。
6. **交互操作归属**：`ops` 章节默认仅输出到 Excel 操作项列；MD/Word 不输出（可配置）。
7. **表格紧凑**：Word 表格行距 1.0、段前段后 0，控制文档纵向占位。
8. **文件锁定**：生成前确保目标 .docx/.xlsx 未被打开，否则保存失败。
9. **数据可靠性与业务口径**：业务逻辑/数据来源需以真实源码（composables、接口层）为准；`source` 一律采用业务来源描述（设备端动态数据 / 所属系统页面字段 / 系统协议报文），不使用「前端 Mock / store / 接口」等技术术语标注（如"前端 Mock，未对接真实后端"）。

## 七、语言与文字规范（硬性规则，按项目定制后固化到生成代码）

PRD 输出遵循「**非业务英文零残留**」与「**简洁专业的产品语言**」两大硬性规范。

> **通用标准 + 按项目落地**：本章给出的是**通用标准与实施方法**，其中出现的词条/示例仅为说明写法，**不是可直接照搬的固定清单**。落地新项目时，必须根据该项目的实际业务——字段名、权限点、页面结构、业务数据出处——重新生成对应的映射词典、校验白名单与示例，再固化到该项目的渲染层（`prd_render.py`）、扫尾脚本（`_cleanup_md.py`）与校验门禁（`check_english.py`）中，不得把其他项目的落地内容原样照搬。

### 7.1 非业务英文零残留

- **目标**：除业务数据（本项目字段名、接口返回、协议报文等业务实体）与标准技术缩写外，正文、表头、字段、数据来源、说明、逻辑、操作项中不允许出现英文单词、代码标识符、函数名、路由路径、组件名。
- **规则来源**：`check_english.py` 校验门禁，白名单（`STOP`）之外的英文词种数必须为 0 才视为通过；生成后须运行校验确认。
- **保留范围（白名单）**：
  - **标准技术缩写**（网络/协议/加密/格式/单位等通用缩写，按本项目实际涉及的范围登记）：如 IP、IPv4/IPv6、MAC、TCP、UDP、ICMP、ESP、GRE、VLAN、ACL、NAT、IKE、IPSec、VPN、HA、DNS、ARP、CSV、MTU、NTP、CA、HTTP(S)、URL、API、JSON、XML、DER、PEM 等；
  - **业务英文**（本项目字段名/接口/路径等承载真实业务语义的标识）：由项目团队按实际业务登记；翻译层可自然转为中文的优先转中文；无法自然翻译或翻译后丢失标识语义的保留，且必须登记进校验白名单；
  - **单位/标准量纲、文件名模板、固定示例值**等（如 `YYYYMMDD_HHmmss.csv`、`UTC`）。
- **必须中文化（禁止出现在最终文档）**：
  - 权限点/操作编码：按本项目权限模型生成映射，通用写法为「`模块:页面:操作` → 模块-页面-操作」（具体词条以本项目权限表为准，如 `a:b:c` → 模块A-页面B-操作C）；
  - 页面/组件文件名：映射为页面中文名（如 `XxxPage.vue` → 对应页面中文名、`el-dialog` → 弹窗）；
  - 代码语法与实现细节：改写为业务表达（如 `store.xxx` → 数据仓库·中文、`xxx.includes(关键字)` → 按 xxx 包含匹配、`true/false` → 是/否、`==` → 为、`:` → -、`localStorage` → 本地存储、`Blob` → 二进制对象、`ElMessage` → 顶部消息）。

### 7.2 功能说明语言规范（funcs）

- 第 1 条以「概述：」开头，一句话概括 **核心定位 + 整体作用 + 全部能力清单**；定位用业务语言（"是××的入口/用于××"），能力按业务维度罗列（认证/守卫、配置、下发、监控等），用「、」「，」串联。
- 后续每条以无序列表 `- ` 输出，一**条一个能力点/场景规则/展示形态**，每条约一句、主谓宾完整、不省略主语，禁止贴代码片段或函数名。
- 统一用产品术语：弹窗、抽屉、页签、下拉、开关、标签、表格、分页组件；禁用「Mock / store / computed / v-if / router」等前端实现词汇。
- 同一字段/概念全文用词一致：取本项目规范化的中文名（如本项目业务字段规范名为「资源名称」，则全文统一用「资源名称」，不混用其英文标识或「名称(name)」式写法）。

### 7.3 业务逻辑语言规范（logic）

- 每条以「场景前置：结果」句式组织，覆盖：表单校验规则、数据生成/刷新时机、失败计数与锁定、守卫/拦截分支、提交成功/失败的不同提示与跳转、对账/合并规则、权限控制等。
- **场景判定必须写明「触发条件 + 拦截/放行 + 提示文案」三段**：不同场景用独立条目分别描述，判定条件（何时触发）、动作（阻止/允许/自动执行）与提示文案（『』包裹，尽量还原前端原文）缺一不可。典型判定场景包括：
  - **删除引用判定**：删除某配置前先检查其是否被其他模块引用，命中引用时阻止删除并提示「不可删除，当前xxx已在xxx已配置使用，请在xxx删除引用后才可删除」（引用模块按业务优先级取第一个命中项）；无引用才进入二次确认/风险确认。示例：删除网桥前检查该网桥是否被 路由配置（出接口）、ARP配置（接口/转发接口）、高可用性配置（桥接口）引用。
  - **批量操作整批判定**：批量删除/清空时任一选中项存在引用则整批阻止，并提示首个被引用项。
  - **风险操作二次确认**：删除/修订可能导致网络中断等影响时，引用判定通过后弹风险确认（如「删除网桥，可能会导致该设备网络中断，是否继续提交？」），确认后才执行。
  - **唯一性校验**：新建/编辑时同维度字段不可重复（同设备名称、同一接口下 VLAN 编号等），重复时提示并阻止保存。
  - **默认值/联动规则**：如默认路由开启后目的地址固定为 default/0；仅保留 1 条默认路由（自动取消其他标记）。
  - **条件必填与格式校验**：联合字段任一有值则其余必填；必填缺失、格式非法（长度、字符集、IPv4、MAC 等）分别提示并阻止提交。
  - **状态/角色派生**：按部署模式或角色自动派生展示值（主备→主机/备机、单机→单机），并限制不可操作项（系统管理员角色不可操作等）。
- **数据来源一律业务口径**：描述本项目实际的数据出处（设备端动态数据 / 所属系统页面字段 / 系统协议报文 / 第三方下发报文等，按项目实际界定），不得出现「前端 Mock / store / 接口 / 模拟数据」等实现层表述。
- 提示文案用『』包裹；状态/枚举用中文（已注册/未注册/已关闭、在线/离线/异常、启用/停用、通过/阻断等，按项目实际枚举枚举值中文化）。
- 数值与格式约束写具体范围（如 1-64 字符、16-32 位、IPv4、1-65535，按项目实际约束填写），不引用校验函数名（不写 `checkXxx`，写「校验某字段格式」）。

### 7.4 字段表语言规范（io）

- 字段名渲染前经 `_field_cn` 清洗为**纯中文**：剥离「中文名 英文标识」中的英文部分、去冗余括号、去重复片段，保留本项目认可的通用业务缩写（如 IP/MAC/HA 等，按项目实际决定取舍）。
- 字段类型用中文枚举（文本/数值/布尔/枚举/日期/日期时间/数组/对象/文件/树/多行文本 等）。
- 数据来源落到本项目实际业务出处（如「XX管理页/XX字段」「设备端下发报文」，按项目实际填写），不写「前端录入/前端 Mock/接口返回」。
